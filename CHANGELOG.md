## [Unreleased]

### Fixed
- `TicketDeliveryTest` failed in some full runs and passed alone (csp-ticketing-api#76): `makeDue` set `next_retry_at` from the clock of the PostgreSQL container (`now() - interval '1 second'`) while the service compares it with the clock of the JVM, and the two clocks differed by up to about 1.4 seconds in the runs measured, so a delivery meant to be due was not. It now sets the instant from the clock of the JVM. Only the test changed; the service already reads one clock (the injected `Clock`).
- `POST /internal/tickets/{ticketId}/pdf` accepted any `pdfUrl` of up to 500 characters, so a caller could make a ticket point to another address (csp-docs#292, threat T). `PdfUrlPolicy` now accepts only `s3://<bucket>/<key>` of `OBJECT_STORAGE_BUCKET` (what csp-worker reports) or an `http(s)` URL on the host and port of `OBJECT_STORAGE_URL`; another host or bucket, credentials in the address, another scheme, an empty key, `..` or a fragment answer `400 INVALID_REQUEST` and nothing is stored.
- Tests for csp-docs#293: the registration of the PDF answers `401` without a token and with a user token, `403` to a service of another subject and succeeds for `csp-worker`; `/me/tickets` and `/me/notifications` answer `401` without a token and `403` without `ticket:read:self`. A user token on `/internal/**` is `401` and not `403` (ADR-056: a user token is never a service credential).
- Two copies of the same event consumed at the same time passed the inbox check together and the second failed on the unique key of `inbox_event`, so its message was rolled back and retried instead of being recognised as processed. `InboxEventRepository.tryInsert` is now one `INSERT … ON CONFLICT (event_id) DO NOTHING`. The unused `markFailed` and `InboxEvent.of` are removed (HU-TICKETING-003, FR-TICKETING-003).
- Two concurrent reports of the PDF of one ticket (`POST /internal/tickets/{ticketId}/pdf`) both saw it without PDF and wrote one `TicketIssued` row each (8 rows for 8 calls). The ticket is now read with a row lock, so one row is written. `DuplicateProcessingRaceTest` covers the inbox, the same reservation under several events and the PDF report.
- Two overlapping runs of `POST /internal/fulfillments/dispatch` read the same pending deliveries and both sent the email, because nothing claimed a delivery before sending. Each delivery is now locked with `FOR UPDATE SKIP LOCKED` for the whole transaction that sends it, so a run skips what another run holds or has already sent. A crash between the send and the commit can still repeat one email (HU-TICKETING-003, FR-TICKETING-003). `overlappingDispatchRuns_sendEachEmailOnce` runs two dispatches at once.
- A concession order that arrives before the booking was never stored: the pending order inserted its items as text into a `jsonb` column and the transaction failed, so the message was retried and dead-lettered unless the ticket appeared in the meantime. `PendingConcessionOrder.itemsJson` is now mapped as JSON, like the JSON columns of `Ticket` (HU-TICKETING-002, `csp-ticketing-api#5`). The test that exercised this path only passed through those retries; it now waits for the inbox row of the concession event.
- The booking and the concession order of a reservation are consumed by two listeners at the same time and each looks for what the other stores, so both could miss it and leave the ticket without its concessions, with the pending order orphaned. Both handlers now take a transaction lock per reservation (`pg_advisory_xact_lock`), and `ConcessionBookingRaceTest` runs 80 pairs at once.

### Changed
- `deploy/compose.yml` passes `TICKETING_SMTP_AUTH` and `TICKETING_SMTP_STARTTLS` (default `true`, so qa and main do not change) as `SPRING_MAIL_PROPERTIES_MAIL_SMTP_AUTH` and `SPRING_MAIL_PROPERTIES_MAIL_SMTP_STARTTLS_ENABLE`. The development catcher has no authentication and no TLS, so with the settings forced on `/health/ready` reported `emailProvider` down (`no password specified`) although the catcher was up; the platform env file of development now sets both to `false` (code-corhuila/csp-ticketing-api#71).
- `deploy/compose.yml` reads domain variables of the platform (`TICKETING_APP_USER`, `TICKETING_APP_PASSWORD`, `TICKETING_FULFILLMENT_PASSWORD`, `TICKETING_SMTP_*`) and builds the datasource URL from `PG_DATABASE`, instead of `SPRING_DATASOURCE_*` and `RABBITMQ_*` names that collide with csp-booking-api and csp-worker in the shared environment file (csp-infra-postgres#41).
- `target/` was tracked (49 files, including an empty `core` jar that produced an application without the `core` module); it is removed from the index and ignored with `.env` and `keys/`.
- The integration tests build their schema by applying the migrations of `csp-ticketing-db` with Flyway (the `sql` folder of the sibling checkout, or `-Dticketing.db.dir`) instead of keeping a copy of it, so they cannot drift from the deployed schema. `ProjectionApp` moved out of the package that `TicketingApplication` scans, and `TicketingApplicationTests` no longer allows bean definition overriding (HU-TICKETING-002 follow-up).
- Tests for `ConcessionOrderConfirmed`: the full payload of `csp-concessions-api` (name, quantity and unit price of every line, product and combo) and a redelivery with the same `eventId` that must not change what was stored.

### Added
- HU-TICKETING-005, scenario 2, second part (csp-ticketing-api#70, ADR-068): the HOLD_EXPIRY_WARNING notification. `POST /internal/notifications/hold-expiry-warnings?limit=` (service credential of `csp-worker`, `limit` 1 to 100, default 50, `400 INVALID_REQUEST` otherwise) creates, in one transaction per call, one notification per kept hold that is open, not warned and expires within `ticketing.hold-expiry-warning.lead-seconds` (default 120, env `HOLD_EXPIRY_WARNING_LEAD_SECONDS`), skipping the reservations that already have a ticket or a `RESERVATION_EXPIRED` notification (the events of a reservation use different queues, so one can arrive before the hold). Each reservation is locked and its hold read again under the lock, so overlapping runs warn it once. The hold is marked as warned and the call answers `{"warned": n}`. The message is in Spanish with the minutes left rounded up, in the singular for the last minute, and no clock time. `NotificationRecorder.record` now tells whether it stored the notification. Requires the first part.
- HU-TICKETING-005, scenario 2, first part (csp-ticketing-api#70, ADR-068): the service consumes `ReservationHeld` of Booking (`cine.booking.reservation-held.v1`) from the queue `cine.ticketing_fulfillment.reservation-held` with its dead-letter queue, applies it once per `eventId` and keeps the hold in `held_reservation` (csp-ticketing-db V012) once per reservation. An event without `expiresAt` (published before the field) is accepted and not stored; an invalid one goes to the dead-letter queue without retries. `BookingConfirmed` and `ReservationExpired` mark the hold as resolved under the same lock of the reservation. The parsing of the Booking envelopes is shared (`EnvelopeFields`). The reminder itself follows in the next change. Requires csp-ticketing-db V012 and, for the instant to arrive, csp-booking-api#89.
- `GET /api/v1/ticketing/me/tickets` (csp-ticketing-api#68, contract `ticketing-fulfillment-service.yaml`, page `My Tickets`): lists the tickets of the authenticated user (the `sub` of the token) by showtime start and then by creation, newest first, the ones without a start time last, paginated with `page` and `limit` like `/me/notifications` (`400 INVALID_REQUEST` when they are out of range). Each ticket carries its display snapshot, seats, concessions (name and quantity, no prices), `qrPayload`, `pdfUrl` (the path of `GET /me/tickets/{ticketId}/pdf`, or null until the PDF exists, never the internal reference of the storage), `deliveryStatus` of its delivery and `createdAt`. The check of `page` and `limit` and its error answer are shared by both lists (`InvalidPaginationException`, `PaginationExceptionHandler`).
- HU-TICKETING-005, second part (csp-ticketing-api#66): the service consumes `ReservationExpired` of Booking (`cine.booking.reservation-expired.v1`) from the queue `cine.ticketing_fulfillment.reservation-expired` with its dead-letter queue, applies it once per `eventId` and creates the `RESERVATION_EXPIRED` notification of the user, once per reservation, in Spanish and with the instant the hold expired; a message that can never succeed goes to the dead-letter queue without retries. The queue is declared at start with the others and the login of the service may configure it (ADR-036). The event catalog of csp-docs must list Ticketing as a consumer.
- HU-TICKETING-005 (FR-TICKETING-005, csp-docs#218), first part: `GET /api/v1/ticketing/me/notifications` lists the notifications of the authenticated user (the `sub` of the token), newest first, paginated with `page` (from 1) and `limit` (1 to 100, default 20) and answering `data` and `meta` (`page`, `limit`, `total`, `totalPages`); a wrong `page` or `limit` is `400 INVALID_REQUEST`. The table `notification` of csp-ticketing-db V011 stores them, one per reservation and type, so a redelivered event creates no second one: `BOOKING_CONFIRMED` is created with the ticket when `BookingConfirmed` is processed and `TICKET_ISSUED` when the PDF of the ticket is registered, both in the same transaction as the change and in Spanish. `RESERVATION_EXPIRED` (the `ReservationExpired` event of Booking), `HOLD_EXPIRY_WARNING` (needs the expiry instant in `ReservationHeld`) and `GET /me/tickets` are not implemented yet. Requires csp-ticketing-db V011.
- Pipeline (Annex I): `.github/workflows/ci.yml` builds and tests every pull request into `develop`, `qa` and `main` with JDK 21 (`mvn -B verify`), applying the migrations of `csp-ticketing-db` pinned to a commit and read with the deploy key `DB_DEPLOY_KEY`, and fails without it so a green run means the integration tests ran; `.github/workflows/env-tracking.yml` and `.github/pull_request_template.md` come from the template. Until now the repository had no workflow, so criterion 3 of csp-docs#291 (the authorization test runs on every pull request) could not hold.
- `TicketingAuthzNegativeTest` (csp-docs#291, threat S of the hop from the gateway, norm 5.3.7): the application runs as deployed on a real HTTP port with every security filter on, and the requests go straight to that port. Without `Authorization`, with an unsigned token (`alg=none`), with an HS256 token, with an RS256 token signed by another key and with a token without `exp` or `sub` the answer is `401` (the first one in the error envelope with `error`, `message` and `traceId`); the internal operations refuse a user token; the same request with a valid RS256 token gets past the filters. 7 tests.
- The API runs in the platform composition (csp-ticketing-api#54): `deploy/Dockerfile` builds an executable jar (`app/pom.xml` now runs `repackage`, final name `ticketing-app.jar`, it was a plain 34 KB jar with no main manifest) and `deploy/compose.yml` (service `ticketing-api`, network `platform`, `expose` 8084) takes every setting from the platform environment with no secret in the file. The object storage keys stay required at start (ADR-058): the platform provides them.
- Validation of the access token (csp-ticketing-api#12, norm 5.3.7 and 5.3.12, ADR-042, ADR-056): RS256 with the key of `JWT_PUBLIC_KEY` or `JWT_PUBLIC_KEY_FILE`, `exp` and `sub` required, 30 s of clock skew, any other algorithm rejected; the service does not start without the key. `/health` and `/health/ready` need no token; `/me/**` needs a user token (the `sub` is the user id) with `ticket:read:self`; `/internal/**` needs a service credential (issuer `csp-auth`, audience `csp-internal`, `sub` in `SERVICE_SUBJECTS`). Answers: `401 UNAUTHORIZED`, `403 FORBIDDEN` in the single error envelope. Before this the oauth2 resource server had no configuration and the service answered `401` to every request, the health routes and the worker included.
- HU-TICKETING-002 (ADR-058): `GET /api/v1/ticketing/me/tickets/{ticketId}/pdf` streams the ticket PDF to its owner (`application/pdf`, attachment, `private, no-store`); a ticket of another user, an unknown ticket and a ticket without PDF answer `404`, and a storage that cannot give the file answers `503` without describing the storage. The API reads the private bucket through the S3 API with a read-only account (`OBJECT_STORAGE_URL`, `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY`, `OBJECT_STORAGE_BUCKET`; the secrets have no default and the API refuses to start without them). `/health/ready` reports `objectStorage`.
- HU-TICKETING-002 (ADR-057): `GET /internal/tickets/awaiting-pdf?limit=` (1 to 100, default 50) lists the tickets whose document is still to be rendered, oldest first, with what the worker needs: ticket and reservation ids, movie, room, start time, seats, concessions and the QR payload. A ticket is offered only after `ticketing.pdf.min-age-seconds` (60 by default), so the concession order that follows the booking reaches it before the document is rendered.
- HU-TICKETING-002 (ADR-057): `POST /internal/tickets/{ticketId}/pdf` records the PDF URL the worker reports and writes `TicketIssued` to the `outbox_event` table in the same transaction, once per ticket; the csp-worker relay publishes it. Requires `csp-ticketing-db` V007.
- HU-TICKETING-002 (ADR-057): `POST /internal/fulfillments/dispatch?limit=` (1 to 100, default 50) sends the emails of the due pending deliveries whose ticket has its PDF: it resolves the contact by `user_id`, keeps the delivery `PENDING` with a growing delay (1 and 5 minutes) when the contact is missing or the email fails, and marks it `FAILED` after 3 attempts.
- The email carries the ticket details and a link to the PDF, not the file. Values from other services are HTML-escaped.

### Changed
- The ticket email links to the tickets page of the portal (`TICKETING_PORTAL_URL`, `/dashboard/tickets`), where the user signs in and downloads the PDF, instead of the stored file.
- The `ObjectMapper` writes dates as RFC 3339 text and understands `java.time`; the plain one of the configuration could not serialize an `Instant`.
- The internal routes answer with the platform error envelope (`error`, `message`, `details`, `traceId`). They are still not authenticated: the service-token check is `csp-ticketing-api#12`.

### Removed
- `GET /me/tickets` and `GET /me/notifications` and the ports `TicketQueryUseCase` and `NotificationQueryUseCase`: they had no implementation, no test and no story in this repository (the contract keeps them for HU-TICKETING-005 and the ticket list of the portal), and they serialized entities. The download of a ticket PDF, `GET /me/tickets/{ticketId}/pdf`, stays.
- `EventPublisherPort` and `RabbitEventPublisher`: the API no longer publishes to the broker (norm 5.3.11).

### Changed
- HU-TICKETING-002 (ADR-057): `BookingConfirmed` no longer fails when the contact projection does not exist yet. The ticket is stored with `user_id` (the contact id stays empty) and its delivery stays `PENDING`. A null `showtimeStartsAt` (Booking sends it until Catalog exists) is accepted and the PDF prints "To be confirmed". Requires `csp-ticketing-db` V007 to V009.
- The Booking and Concessions queues are named `cine.ticketing_fulfillment.booking-confirmed` and `cine.ticketing_fulfillment.concession-order-confirmed`, each with its own `.dlq` through `cine.dlx` (ADR-036); the old `ticketing.*` queues must be drained and deleted by hand.
- `BookingConfirmed` is validated like the Auth events: a message that can never succeed goes to the dead-letter queue without retries.

### Fixed
- The service starts (HU-TICKETING-002): `TicketingController` needed `TicketQueryUseCase` and `NotificationQueryUseCase`, which nothing implemented, so the application context could not be built and `TicketingApplicationTests` failed in `develop`. That test is now a real one (PostgreSQL with the schema and RabbitMQ in containers, the real configuration) and passes.
- `GET /health/ready` reports the real state of `database`, `broker`, `consumers`, `emailProvider` and `objectStorage`; it reported `UNKNOWN` for all of them because the converter looked for details that a composite health does not have, and `HealthStatusConverter` is gone. The mail sender is declared as `JavaMailSenderImpl`, so the mail health indicator of Spring Boot is registered and `emailProvider` is no longer always unknown.
- The service no longer declares the exchanges `cine.events` and `cine.dlx` (ADR-036): they belong to `csp-infra-rabbitmq` and the login `ticketing_fulfillment` may configure only `cine.ticketing_fulfillment.*`, so against the real broker the declaration was refused with `ACCESS_REFUSED` and no queue or consumer started. The bindings use the exchanges by name. `TicketingQueuesTest` checks it (HU-TICKETING-002).
- The reader of the ticket PDFs gives the region of the storage (`OBJECT_STORAGE_REGION`, `us-east-1` by default) to the S3 client. Without it the client asked for the location of the bucket first, which the read-only account (get on `tickets/*`) may not do, so every read and the readiness check failed with `AccessDenied` against `csp-infra-rustfs`. `S3TicketPdfStorageRequestsTest` checks that a read sends only the `GET` of its key and the check only the `GET` of its probe (HU-TICKETING-002). The bucket check is a `GET` and not a `HEAD`: with the region given, a `HEAD` cannot tell a missing bucket from a missing key, and only the error body does.
- The `TicketIssued` queue is named `cine.ticketing_fulfillment.ticket-issued` and has its own dead-letter queue `.dlq`, like the other queues (ADR-007, ADR-036). It was `ticketing.ticket-issued` with a shared `ticketing.dlq`, names outside what the broker lets the login `ticketing_fulfillment` configure (`cine.ticketing_fulfillment.*`), so the declaration was refused. `TicketingQueuesTest` checks every declared queue against that pattern and the dead-letter wiring (HU-TICKETING-002).
- The JPA repositories could not be created (`findByUserContactId` and `findPendingForRetry` were not valid queries), so no ticket could be stored. The unused `findByUserContactId` methods are removed and `findPendingForRetry` is a real query.
- `ConcessionOrderConfirmedConsumerTest` never ran (no schema, bean clash with the projection test); its scenarios, the concession arriving before or after the booking, are now in `BookingConfirmedConsumerTest`.

- Consumer resilience (HU-TICKETING-001, `csp-ticketing-api#7`): when the broker cancels a consumer or deletes its queue, the listener container declares the queues, dead-letter queues and bindings again and subscribes again with exponential backoff (1 s doubling up to 30 s, no attempt limit). A WARN names the queue (never the payload) and an INFO plus the `ticketing.consumer.resubscriptions` counter record the resubscription.
- `/health/ready` reported the consumers through a bean that looked for listener containers among the Spring beans, where `@RabbitListener` containers are not; the `consumers` indicator now reads them from the listener registry and is DOWN while any container has no subscribed consumer.
- The booking-confirmed, concession-order-confirmed and ticket-issued queues and their bindings were built but never declared; they are now part of the declared topology.
- `application.yml` declared `spring.rabbitmq` twice, which Spring Boot rejects at start-up; the connection settings are merged into one block.
- `Ticket` JSON columns (`seat_labels_snapshot`, `concessions_snapshot`) are mapped with `@JdbcTypeCode(SqlTypes.JSON)`, without which the entity manager failed to build.
- The test sources compile again (a duplicated variable in `ConcessionOrderConfirmedConsumerTest`; `ConsumerResilienceTest` called an API that does not exist and is removed, its resilience scenarios return with HU-TICKETING-001 issue #7).
- Auth event queues are bound to the contract routing keys `cine.auth.user-registered.v1` and `cine.auth.user-email-changed.v1` (they were declared but never bound, and with the wrong keys), and are named `cine.ticketing_fulfillment.*`, each with its own `.dlq` through `cine.dlx`.
- Listeners acknowledge automatically (manual mode with a `void` listener never acknowledged), retries follow ADR-007 (5 s, then 25 s) and no longer run twice, and rejected messages are dead-lettered through `cine.dlx`.
- Contact emails are no longer logged.

### Added
- HU-TICKETING-001: the contact projection applies only events newer than the stored `last_updated_at`, normalizes the email to lower case, and validates the Auth event envelope; invalid messages go straight to the dead-letter queue.
- Unit, contract and integration tests (PostgreSQL and RabbitMQ with Testcontainers) for `UserRegistered` and `UserEmailChanged`.
